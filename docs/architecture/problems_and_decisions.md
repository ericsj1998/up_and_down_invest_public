# 겪은 문제와 내린 판단 — 중요도 순 기록

> 실계좌가 도는 자동투자 플랫폼을 혼자 만들면서 **무엇이 깨졌고 · 왜 그랬고 · 어떻게 고쳤고 · 다른 선택지는 무엇이었고 · 결과가 어땠나**를
> 한 곳에 모은다. 사고 순서가 아니라 **중요도 순**이다 — 돈에 닿았나 · 얼마나 오래 몰랐나 · 다시 날 수 있나.
>
> 숫자는 전부 이 저장소의 실측 기록에서 옮겼다(출처를 항목마다 적었다). 문서와 코드가 어긋난 곳은 **코드를 기준으로 정정**했고 그 목록을 §7 에 따로 뒀다.
> 매매법의 규칙·임계값·성과는 비공개라 여기 없다 — 이 문서는 **플랫폼의 판단**만 다룬다.

읽는 법: 면접에서는 "정의 한 문장 + 내 코드에서는 이렇게 한 문장"이 한 세트다. §3 이 그 형식이고, §1·§2 는 그 답의 근거가 된 사고들이다.

## 0. 한 문단 요약

코인 선물(2개 거래소)과 주식(페이퍼)을 같은 세션 엔진으로 굴리는 시스템이다. 핵심 난제는 전략이 아니라
**"앱이 믿는 것(원장)과 거래소가 들고 있는 것(사실)을 어떻게 일치시키는가"** 였고, 가장 큰 사고 아홉 개 중 일곱이 그 이야기다.
두 번째 난제는 **"측정이 스스로를 속이지 않게 하는 것"** — 미래 참조 · 결과만 재는 표 · 연구 엔진과 운영 엔진의 차이 · 데이터 결손을 어떻게 잡았나.
세 번째는 **1 GB 서버 한 대**에서 배포·폴링·호출 예산을 어떻게 살았나.

| 규모 | 값 |
|---|---|
| 기간 · 커밋 | 2026-08-02 ~ · 1,300+ 커밋 |
| 백엔드 | Python 3.12 · FastAPI · SQLAlchemy 2 async · PostgreSQL 16 · Redis · 약 12만 줄(`src/`) |
| 프론트 | React 18 · TypeScript strict · Vite · Lightweight Charts |
| 검사 | ruff(docstring 포함) · pyright strict · import-linter 계약 4 · pytest 4,300+ · AST 가드 시험 |

## 2. S 등급 상세 — 네 단계로

각 사고를 ① 무엇이 문제였나 ② 왜 그렇게 됐나 ③ 어떻게 고쳤나 ④ 다시 하면 무엇을 다르게 — 로 적는다. 면접에서 "실패담" 을 물으면 여기서 고른다.

### 2.1 봉 사이 체결을 원장이 4시간 몰랐다 (2026-09-06 · 실계좌)

① 실계좌 코인 선물 지정가(29 계약 · 배율 5)가 12:04Z 에 전량 체결됐는데 원장은 "대기" 였고 조건부 손절이 없었다. 콘솔은 "고아 포지션" 과 `ledger_mismatch` 를 번갈아 띄웠다 — 두 감시가 같은 사실을 다른 문턱으로 봤다(점검은 2회 연속이어야 경보 · 대조는 즉시).

② 체결 확인(`_pump_fills`)과 원장 기록(`_collect`)이 **걸음 안에만** 있었고, 실계좌 급전은 진입 축(4h) 봉 마감에서만 걸음을 준다. 08-18 사고 때 **청산**은 점검 루프로 내렸는데 **진입 체결**은 걸음에 남겼다 — 15m 급전에서는 최대 15분이라 안 보였고, 4h 급전이 실계좌에서 처음 돌자 4시간이 됐다. `_guard_stop` 은 원장이 포지션을 알아야 손절을 걸기 때문에 "경보는 맞았는데 고칠 자리가 없었다".

③ 점검 루프가 우편함을 채우고(`_absorb_between_bars`), 전량이면 봉을 기다리지 않고 원장에 적은 뒤 즉시 손절(`Session.absorb_fills`). 봉 마감과 봉 사이가 **같은 헬퍼**를 쓰고 걸음과 **같은 자물쇠** 안에서 돈다. 대조는 그 판이 기다리는 체결을 고아(error)가 아니라 **반영 대기(warn)** 로 분류한다. 회귀 시험 `tests/test_fill_between_bars.py` · 로그 `live_fill_absorbed`.

④ 첫 배포는 문이 잘못 잠겨 있었다 — 복원이 표를 우편함에 넣고 `resting` 을 비우는데 문은 `resting()` 을 봤다. 점검 루프가 6번 돌고도 안 옮겼고 두 번째 배포에서 고쳤다. 실측 무방비 **1시간 21분**(수정 없었으면 **3시간 56분**). 다시 하면: **비동기 사실(체결)을 판정 주기에 묶지 않는다.** 짧은 축에서 안 보이는 결함은 축을 늘리면 드러난다 — "재시작 뒤 무엇이 죽나" 표를 설계 단계에서 썼어야 했다.

### 2.2 원장이 팔지도 않은 가격에 팔았다고 적었다 (2026-08-19 · 모의)

① 같은 매매를 원장은 거의 전부 이익으로, 실제 청산가로 다시 재면 거의 전부 손실. 화면 수익률이 **부호까지** 뒤집혀 있었다. 자가 점검은 "잔액이 갈렸다" 만 말했고 그건 이미 다 잃은 뒤였다.

② `exit_average` 가 반익 절반을 **언제나 계획가**로 계산했다. 구분자(`half_by`)는 이미 있었는데 쓰는 쪽이 안 읽었다. 더 나쁜 것: 원장만 반익을 적고 **거래소에는 감축 주문이 안 나갔다**.

③ `half_by` 를 읽고 **`half_price`(얼마에 덜었나)** 필드 신설 · 반익의 실제 집행 배선 · 회귀 시험. 그 이전 청산 88건은 손익이 틀려 리포트가 컷오프를 들고 다닌다 — 고쳐도 과거 표는 못 고친다.

④ **판단의 근거로 쓰는 숫자 자체가 틀리면 조용하다.** "원장 실현손익 합 vs 거래소 실현손익" 감사가 그때 없었고 3시간 동안 아무도 몰랐다. 같은 날 겹친 결함 5개가 3시간에 36번 진입했고 계좌 −100 USDT 중 64 가 순수 수수료였는데 원장은 +7.8% 를 찍고 있었다.

### 2.3 배율을 안 걸어 40초마다 같은 고리를 돌았다 (2026-08-20 · 모의)

① 진입 → 기하 차단 → 손절 3회 실패 → 시장가 청산 → 재진입. 자가 점검이 늘 붉었다. 거래소 거절 메시지 `margin 461 while available 24` 의 산수가 정확히 맞았다 — 예산 × 다리 비중 × 원장 배율 20 = 명목, 거래소 실제 배율 3 → 증거금 460.

② `set_leverage` 는 **사람이 화면에서 "배율 바꾸기" 를 누를 때만** 불렸다. 그 외 여섯: 지정가로 산 매매가 시장가 경로로 새어 두 배 진입 · 본절 손절을 거래소가 발동가 규칙으로 거절 · 자가 점검이 본절을 이상으로 오탐 · 지정가 경로에만 증거금 검사가 없음 · 다판에서 대조식 불성립 · 겹쳐 쌓인 포지션을 아무도 안 셈.

③ 판이 뜨면 배율부터 맞추고 못 맞추면 **주문을 아예 안 낸다**(`observe_only`) · 보호(손절·익절)를 진입 경로에서 분리(`_place` / `_protect` / `_arm`) · 발동가 거절엔 **1틱만** 완화 · 두 진입 경로가 같은 계산 · 겹쳐 쌓임 경보.

④ 거절된 것이 다행이었다 — 통과했으면 원장과 실제가 배율 배수만큼 조용히 갈렸다. **기존 단위 시험이 잡은 결함은 0/7** — 부품은 전부 정상이고 틀린 것은 "A 가 B 를 안 부른다" 였다. 그래서 호출 관계를 읽는 시험을 일부러 넣었다(33건).

### 2.4 OS 업데이트가 백엔드를 죽였고 방어선이 비어 있었다 (2026-08-20)

① Windows Update 가 WSL 을 갈아 끼우며 VM 을 내렸다. 컨테이너는 `restart` 로 복귀했지만 **호스트에서 돌던 api·web 은 영영 안 왔다**. 그 순간 포지션 4개 중 3개에 거래소 조건부 손절이 **0건**.

② 발동가가 현재가 반대쪽이라는 거절(= **이미 손절선을 지났다**)을 코드가 단순 실패로 세고 3회를 기다렸다 · 발동가를 호가 눈금에 안 맞춰 영영 안 걸리는 손절이 있었다 · 진입 조건에 "지금 지킬 수 있나" 가 없었다.

③ 원값·1틱 완화 둘 다 거절이면 `StopBlownError` → **즉시 청산** · 발동가를 눈금 배수로 · `guarded=False` 로 **새 진입만** 차단(손절 재장착·청산은 계속) · 화면·API 를 컨테이너로. 시험 14건.

④ 정직한 한계: Docker Desktop 도 WSL 위라 컨테이너화가 바꾸는 것은 "영영 안 옴 → 1~2분 뒤 옴" 뿐이다. 공백을 진짜로 없애는 것은 **거래소 조건부 손절**이고, 그래서 뒤에 리눅스 서버로 갔다. `auto`(사람이 멈춤)와 `guarded`(집행이 못 지킴)를 합치지 않은 것이 핵심 결정.

## 3. 질문 묶음별 — 정의 한 문장 · 내 코드 한 문장

### 3.1 정합성 · 분산

**멱등성.** 정의: 같은 요청이 두 번 도착해도 결과가 한 번과 같아야 한다. 우리: 클라이언트가 만든 키를 **브로커 주문 이름에 박아** 같은 키의 두 번째 주문을 브로커가 거부하게 한다.

- 키 구성 `{판 뒤6자}-{매매 앞8자}-{종류 2글자}-{다리 번호}` (`orchestration/walkforward/order_mapping.py`). 손절은 다리 자리가 **개정 번호** — 본절 상향이 rev1 이라 키가 달라져야 브로커가 새 주문으로 받는다.
- 거래소별 변환: 콜론 거부·30자 제한 → 접두 + 치환 / 36자 제한 → 절단 시 경고 로그. 절단으로 멱등 범위가 좁아질 가능성은 리뷰에서 재평가해 실제 길이가 제한 안임을 회귀 시험으로 잠갔다.
- **DB unique 제약인가?** 아니다. 스펙 시절 `orders.idempotency_key UNIQUE` 는 있었지만 그 표들은 미사용으로 드롭됐고, 실제 라이브 표의 유일키는 `(run_id, trade_id, role)` 이다. ⇒ 멱등성 강제는 **거래소 서버 + 애플리케이션**이다.
- **재시도 전 체결 조회.** 주문 HTTP 층은 `NO_RETRY` — 층이 절대 재전송하지 않는다. 러너의 `_place()` 도 재시도를 아예 안 한다("재시도 경로를 두면 확인 없이 다시 보내는 코드가 생긴다"). 조회는 `find_order()`(404 → None) · 없는 주문은 `PENDING` 으로 두고 FAILED 로 접지 않는다.

**주문 응답을 못 받았을 때.** 순서: ① 보내기 **전에** `placed[trade_id] = sending` 표시(남아 있으면 "보냈는데 응답을 못 받았다" 의 흔적) → ② 대기 계획을 걸음마다 DB 에 영속 → ③ 재기동·승격 시 `adopt` → `restore_pending`: 거래소 열린 주문과 대조해 **이어받기 / 재요청 / 체결로 / 버리기** 4갈래, 이어받지 못한 내 접두 지정가는 좀비로 취소 → ④ 봉 사이 체결 흡수 → ⑤ 주기 대조. 자동 "타임아웃 → 재전송" 루프는 **없다** — 복구는 대조와 복원이 맡는다.

**원장과 거래소가 갈리는 이유 여섯**(시점 · 기억의 위치 · 부분 체결 · 조건부 만료 · 사람 · 강제청산)과 결정: **자동 싱크를 만들지 않는다.** 원장을 자동으로 고치면 결정론이 깨지고, 거래소를 자동으로 닫으면 손익이 사람 모르게 확정된다. 갈린 사실을 4축(A 무주공산 / B 유령 원장 / C 잔재 / D 부분 무방비)으로 **이름 붙여 내놓기만** 하고 판단은 사람에게. 상세: [ledger_reconciliation.md](ledger_reconciliation.md).

**주기 대조 — 놓치는 구간.** 세 층: 러너 점검 **60초**(문서는 30초라 적혀 있지만 코드는 레이트리밋 때문에 2026-09-01 에 60초로 올렸다 · §7) · 전 거래소 대조 120초 · 판 감시자 60초. 놓치는 것: 탐지 지연 자체는 점검 주기만큼 남는다 · 반쪽 대조는 성공으로 세지 않는다(못 본 거래소의 고아를 "없다" 로 읽는 것이 최악) · 부분 체결 진입 복원은 실전 표본 1건 · 체결 시각 정규화 열은 아직 없다.

**Redis 리더 락 — 만료된 사이 구 리더가 살아 있으면.** `SET NX PX`(TTL 30s · 갱신 10s · `renew > ttl/3` 이면 설정 거부) + 갱신·해제는 **토큰 일치 시에만** Lua. 갱신 실패 = 즉시 상실 → 스케줄러·거래 정지. **펜싱 토큰·세대 번호는 없다** — 문서가 한계를 명시한다: "Redis 락에는 이론적 취약점이 있다 … **중복 주문의 최종 방어선은 멱등키**". Redlock 을 안 쓴 이유: "'락 상태를 모른다' 와 '락이 없다' 를 구분하려면 분산 합의가 필요하고 그 복잡도를 살 이유가 없다". 라이브러리 `Lock` 대신 직접 구현한 이유: 락을 **잃는 순간**을 감지해 거래를 멈춰야 하는데 라이브러리는 그 콜백 지점을 노출하지 않는다. **Redis 불통이면 락 없이 거래를 진행**한다 — 가용성 우선(손절 관리를 Redis 하나에 묶는 것이 더 위험). ⚠️ 검토에서 잡힌 잔결함: 배포 겹침 중 Redis 가 잠깐 끊기면 둘 다 거래 가능 → 부팅 직후 창에서는 실패 시 닫힘으로(열린 항목).

**블루그린 — 전환 순간 양쪽에서 도는 것을 무엇으로 막나.** 드레인이 아니라 **리더 락**이다("무중단 = 프로세스가 안 죽는 것이 아니라 거래 리더가 끊기지 않는 것"). 3중: ① 트레이더 락 ② 팔로워가 거래 POST 를 받으면 **503 + Retry-After 5** ③ nginx `proxy_next_upstream http_503 non_idempotent` + `resolve` 5초. 절차: 마이그레이션 먼저(실패하면 옛 슬롯 무손상 중단) → 빈 슬롯 기동·팔로워 확인 → 옛 슬롯 stop(grace 30s · 락 놓음) → 승격 대기 → RUN 입양. 되돌림은 스키마를 되돌리지 않으므로 **확장 → 배포 → 수축** 하위 호환이 필수. 스케줄러가 양쪽에서 도는 문제는 엔진 리더 락(`updown:engine:leader`)이 따로 막는다 — API 거래 락(`updown:api:trader`)과 키가 둘로 분리돼 있다.

### 3.2 LLM · 에이전트

**도구 15종, 컨텍스트 주입, 라우팅.** 매 왕복 **전부** 넣는다(사전 필터 없음) — OpenAI 호환 function calling 스키마, `tool_choice="auto"`. 라우팅은 모델이 한다: 도구 설명이 "한국어 한 문장 + 유사어 목록" 이고 의도 분류 규칙은 없다. 제공자는 NVIDIA NIM 하나, 모델 풀 6종을 설정으로(동시 팬아웃 또는 폴백 사슬). 근거: [ai_agents_and_mcp.md](ai_agents_and_mcp.md).

**없는 도구 · 잘못된 인자.** 모르는 도구는 예외가 아니라 `{"error": "모르는 도구: …"}` 를 `tool` 역할 메시지로 모델에게 되돌린다. 잘못된 인자는 도구가 `ValueError` 를 던지고 루프가 `{"error": …[:300]}` 로 바꿔 되돌린다 — 턴은 죽지 않는다. **재시도 루프는 0**, 모델이 다음 왕복에 스스로 다시 부르는 것이 유일한 재시도.

**무한 루프.** `MAX_ROUNDS = 6` (모델 호출 최대 7회). 마지막 회차는 도구 호출이 있어도 무시하고 본문으로 마감. **같은 도구·같은 인자 반복 탐지(dedup)는 없다** — 상한을 먹은 사례가 실측에 기록돼 있다. 멀티 에이전트(T277)는 위상 자체를 **순환 없이**(fan-out → fan-in) 둬서 종료 조건이 필요 없다 — 되돌려 보내기(순환)가 필요해지면 그때가 LangGraph 재검토 조건이다.

**프롬프트 인젝션 방어.** 정직하게: **전용 코드가 없다.** 사용자 입력은 `.strip()` 과 빈 값 400 만, 도구 출력은 JSON 직렬화 후 6,000자 절단만. 다만 공격면이 좁다 — 도구가 모델에 넘기는 값은 우리가 계산한 수치(봉·지표·재무·거시)이고 자유 텍스트 외부 문서(뉴스 본문·공시 원문)를 컨텍스트에 넣는 도구가 없다. 후속 피해 차단은 구조 쪽: 도구가 전부 읽기 · **주문 도구 없음** · MCP 는 도구별 권한. 공시 경로(T277)는 1단계가 **모델 호출 0**.

**환각의 정의.** "**근거 없는 숫자 칸의 수.**" 대시보드는 모델이 무엇을 보여줄지만 고르고 숫자 칸은 전부 `{"from": "<도구>.<경로>"}` 참조여야 한다. 리터럴 숫자는 `dropped`(명세 결함), 참조는 있는데 도구 결과에 없으면 `missing`(**환각 후보**) — 둘을 일부러 가른다. 채점에 쓰는 것은 `missing`. 확률은 설계상 없다 — "오를 확률" 대신 **과거 빈도**("과거 같은 자리에서 20봉 뒤 오른 비율 58% (n=41)")로 문구를 고정하고, 달력 자료형에는 **방향 칸이 없다**(시험이 잠근다).

**평가 데이터셋.** **사람이 손으로 쓴 골든셋 16케이스**, LLM 심판은 없다("답의 질을 사람 눈으로 채점하지 않는다 — 재는 것은 도구 호출·성공·지연·토큰·근거 없는 칸 수뿐"). 판정은 순수 함수 `judge`. 모든 도구가 어떤 케이스에든 등장해야 한다는 빠짐 방지 시험. 실측(같은 모델): 11/15 → 14/15 → 15/16 — [ai_chat_scenarios.md](ai_chat_scenarios.md). CI 에서는 안 돈다(비용·외부 의존).

**AI 가 가격·수량·타이밍을 정하지 않는다 — 어떻게 강제하나.** ① import-linter 계약 `llm ⇏ decision·execution`(CI) ② `propose_order` 는 모델이 낸 값을 RiskManager `confirm` 에 넘기고 **돌려받은 stop** 을 쓴다(`stop_moved` 로 당겨졌음을 드러냄) · 수량은 정하지 않음 · 코인 아니면 배율 1 · 숏은 `blocked` ③ 결과는 제안으로만 화면에 가고 **사람이 확인 단추**를 누른다. 예외는 자동 실행 모드(동의 문구 버전 일치 · 일 3건 · 노출 30% 상한)이고 그때도 집행값은 RiskManager.

**MCP.** 같은 도구 레지스트리에서 화면 전용 2개를 뺀 **13개**를 Streamable HTTP 로 연다. 개인 토큰(SHA-256 해시만 저장 · 되돌리기 가능) · 도구별 필요 권한(계정 도구는 `ACCOUNT_READ`) · 주문 도구 없음 · 토큰 호출자는 주문·설정 HTTP 경로 403. 이유: **어떤 에이전트 프레임워크든 물릴 수 있다**는 것이 프레임워크 미채택의 대안이다.

**왜 LangGraph 가 아니라 자체 루프인가.** 1차(09-10): 정확도는 프레임워크가 아니라 모델·프롬프트·도구가 주는 사실·검증에서 나온다 · 대화는 2~4왕복 · 긴 작업은 서버 배치 도구로. 2차(09-12 · 멀티 에이전트로 가도 바뀌나): ① 위상이 그래프가 아니다(분기·순환 없음 · `asyncio.gather` 세 줄) ② 이미 같은 것을 한다(참가자 둘 동시 실행 105초 → 87초) ③ 바깥 HTTP 는 한 층뿐이고 AST 시험이 지키는데 프레임워크 클라이언트는 그 층을 지나지 않는다 ④ 진행 중계·상태 보존·폴백 사슬이 이미 있다. **다시 꺼낼 조건 셋**을 표로 못박았다(분기 · 순환 · 체크포인트). 인정한 손해: 그래프 그림 자동 생성.

### 3.3 금융 데이터 · 측정

**Point-in-time / look-ahead.** 정의: 시점 T 의 판단은 T 에 알 수 있던 것만 써야 한다. 우리는 **타입으로 막는다** — `AsOfSequence`(`analysis/context/guard.py`)는 원본 전체를 들고 `__len__` 이 보이는 개수만 반환하고, 경계 밖 접근에 `LookaheadError` 를 던진다(리스트를 잘라 넘기면 잘못된 접근이 "조용한 오답" 이 되고, 봉마다 재슬라이스하면 O(n²)). 경계는 `ts + interval <= as_of`(마감 봉만). 음수 인덱스를 **보이는 길이** 기준으로 푸는 것이 핵심 — 원본 기준이면 `view[-1]` 이 미래 봉이다.

- 재무제표: 기준은 회계 기간 끝이 아니라 **EDGAR 제출 시각 + 1일**. 어댑터는 가진 전부를 주고 시점 정합은 읽는 쪽이 건다 — "어댑터가 최신만 골라 주면 백테스트가 미래 값을 쓴다".
- 구조물 `created_at` = **봉 시각**(벽시계 아님). as-of 조회의 기준이 봉 시각이고, 봉 시각은 입력에서 나오므로 결정론이다.
- 검증: 봉을 60·75·90% 에서 잘라 돌린 결과와 전체를, 잘린 시각 24h 전에 끝난 매매끼리 정확히 비교 — **90회 불일치 0**.
- **검사기를 시험하는 시험**: `orchestration/discovery/cheats.py` 에 일부러 미래를 보는 가짜 신호 6유형(N봉 앞 극값 · 전 기간 척도 · 안 닫힌 상위 봉 · 확인 봉 없는 프랙탈 …)을 심었다. 계기: 첫 검사기가 여유 8봉을 두고 잘라 1봉 앞 치팅을 원리적으로 못 잡았다 — "심어 두지 않았으면 33종 전부 통과를 믿었을 것". 실사고형 하나는 표본의 0.7% 만 해당됐는데 "그 0.7% 가 성과의 전부" 였다.

**평균 R · MDD 정의.** RR 분모는 **계획 손절폭**(`planned_rr = (계획목표−진입)/(진입−계획손절)`), 계획값은 진입 시점에 박아 두고 나중에 레벨이 바뀌어도 안 움직인다(움직이면 달성률이 언제나 100%). 실제 청산가는 따로 적고 괴리는 `achievement` 로. **MDD = 피크 대비, 곡선은 TWR 지수** — 잔고로 재면 입금이 낙폭을 메우고 출금이 없는 낙폭을 만든다. 백테스트에는 입출금이 없으므로 TWR 로 재야 라이브와 **같은 자**가 된다. 백테스트 MDD 는 복리(단리면 과소평가). λ(배율)를 반드시 병기하고 Calmar = 총수익/|MDD|. **총(gross) vs 순(net)** 을 표마다 둘 다 — 판정 함정이 문서화돼 있다(안전마진은 크고 Net 은 음수인 칸이 최상위 등급이던 것 → `Net > 0` 조건 추가 후 5 → 0).

**Out-of-sample 을 언제 고정했나.** **측정 전에 선언한다** — "결과를 본 뒤에 정하면 골포스트 이동". 분할 지점은 결과가 좋은 지점이 아니라 **비율(약 70/30)과 달력 경계**로. 시간 봉인 + 종목 봉인 **4집합**(IS / 같은 종목 뒤 구간 / 안 쓴 종목 전 구간 / 둘 다 — 가장 강함), 오염 정도를 "뒤 구간을 봤나 / 뒤 구간에 맞춰 골랐나" 로 갈라 기록. **봉인을 코드로 강제**: `--until` 을 캔들 로드 지점에 걸고, 합성 전에 자르고, 축을 흔드는 실행에 없으면 **exit 2**, 기본값으로 넣지 않는다(봉인은 의식적 선택). OOS 조회 횟수 **장부**("여러 번 보면 그것도 in-sample"). walk-forward 는 봉인 구간을 먼저 떼고 창을 만든다.

**표본 30 의 근거.** 통계적 도출값이 아니라 스펙에 **선언된 하한**("예: 30건") — 그리고 **바닥이지 안전선이 아니다**: 같은 문턱에서 n=30 이 50.0%, n=736 이 23.8%. 필요 n 은 부트스트랩(200,000회)으로 — 건당 표준편차가 평균의 **189배**라 10거래 이익 확률 35%, 작은 엣지를 95% 로 증명하려면 **1,134거래**. 30 미만은 결론이 아니라 **판정 보류**(화면 회색). 결함 탐지 표본은 다른 자(5건 — "항상 울리는 경보는 경보가 아니다"). **표본은 전제조건, 승자는 OOS** — 느슨한 게이트가 표본이 많은 것은 당연하므로 표본 수로 승자를 정하지 않고, **게이트 완화로 표본을 늘리는 것은 조작**이다(종목·기간 추가만 정당).

**비용 모형.** 체결 틱을 쓰지 않고 호가창 **mid 기준**(틱으로 재면 bid-ask bounce 가 어떤 간격이든 스프레드와 같게 나온다). 편도 = 스프레드/2 + 깊이충격, 폴링 지연은 더하지 않는다(이중 계산). `slippage_source: measured|assumed` + `measured_at` 을 필드로 강제, 출처 없으면 `CostConfigError`. 가정인 칸은 가정이라고 적었다(미국 주식 슬리피지는 장 마감 중 측정이라 자리표시자). **⛔ 비용을 낮춰 전략을 살리지 않는다**("분모 조작") — 반대로 비싸게 잡으면 될 것도 안 된다고 판정하니 양쪽 다 경계. 필요 승률 `P > (1+c)/(1+RR)`, 비용을 **R 단위로 환산**하는 것이 핵심(비용은 가격에 고정인데 R 은 시간축에 비례). 5m 단독 진입 폐기: 익절 거리 실측에 비용을 넣으면 필요 승률 **100.7~100.9%** = 불가능. 정확한 귀속 — 탈락 이유는 **표본이 아니라 비용**(81건으로 표본은 충족). "표본이 없어서" 로 적으면 나중에 표본을 늘려 되살리려 하고 **그건 산수를 못 바꾼다**. 최종 판정 근거는 수치가 아니라 **여유 배수**: 과거 스프레드는 알 수 없으므로 질문을 뒤집어 "이 승률이면 견딜 수 있는 최대 슬리피지는 얼마인가" 를 역산하고 현재 실측 대비 배수(2.0 최소선)로 답한다.

**결과만 재는 표는 계획 결함에 눈이 없다.** 익절 하한을 손절 하한과 같은 값으로 적용한 결함으로 **전 거래 계획 RR 이 정확히 1.00** — 대칭 동전 던지기를 측정하고 있었다. 그런데 익절률·수익률·한계 기여가 전부 정상 범위였고 계획 RR 은 어느 칸에도 없었다. 차트를 눈으로 열어 보고서야 발견. 조치: 계획 분포(`distinct` · `pin_rate` — 시장이 만든 값은 흩어지고 코드가 만든 값은 한 점에 몰린다)를 결과 표보다 **먼저** 찍는다. 규칙: **새 규칙이 값을 만들면 그 값의 분포를 리포트에 싣는다.** 그때 나온 수익률은 인용하지 않는다.

**연구 엔진 vs 세션 엔진.** 연구 엔진(numpy)은 후보를 **거르는** 도구, 세션 엔진은 실계좌·백테스트가 **실제로 도는** 코드. 채택은 세션 재현 뒤에만. 이 규칙이 생긴 이유: 세션 엔진으로 옮기자 같은 창에서 **부호부터 다른** 값이 나왔다 — 원인 ① 손절을 당긴 뒤 배율을 다시 도출하며 승수가 지워짐 ② 손절 판정이 셋 중 둘만 같았다(연구 = 꼬리 터치 · 라이브 = 거래소 trigger 터치 · 세션 백테스트 = 확인 봉 몸통). 사용자 프레임이 정확했다: "백테스트가 종가형인 게 아니라, 종가형 매매법을 실거래에서 터치형으로 구현한 문제" → 매매법 **선언**에 `stop_mode` 를 적고 셋이 같은 선언을 읽는다. 갭은 자동으로 잰다 — 배포 스크립트가 부호·배율 분포 대조에 실패하면 배포를 **거부**. 교훈: **"합이 맞는 것은 상쇄지 동등성이 아니다."** 연구 엔진 Gate 표본이 실제로는 3개월이었다는 발견도 여기서(하위 봉 커버리지가 구간을 잘랐다) — 커버리지는 표본 수가 아니라 **엔진이 실제로 걸은 구간**으로 보고한다.

**데이터 품질.** 주식 봉에 **장외 불량 프린트**(1h 종가 대비 −31%/+45% · 거래량 수백 주)가 섞여 연구 엔진이 가짜 양수 격자를 만들었다(정규장 필터 뒤 사라짐). 전수 조사: 1h 봉의 70~75% 가 장외, 불량은 거의 전부 장외, 결손도 같이 드러났다("표본 부족" 의 절반은 결손). 대응 원칙 = **삭제가 아니라 표시** — 결측 봉은 행이 없으므로 컬럼 플래그가 불가능 → 구간 단위 별도 표 `candle_quality_issues`, `open` 이 있으면 분석 차단. 필터는 연구 스크립트가 아니라 **적재 층**에. 적재 앵커는 **과거로만** 내린다(앞으로 올리면 그 구간을 쓰던 백테스트가 재현되지 않는다 — 재현성은 전략 코드만으로 보장되지 않고 입력 경계도 고정돼야 한다).

**사람 눈 라벨링 금지(#11) · 권위 아닌 성과(#12).** 정답지를 사람 눈으로 만들면 배제하려던 재량이 시스템의 근본에 다시 들어오고 **그 사람이 틀렸을 때 검출할 방법이 없다**. 대체: 백테스트 성과 + 후속 이행률(손절 전 1차 익절 = 이행 · 같은 봉이면 손절 우선), 구간은 R²·기울기·낙폭. 구분 기준: "그 판단이 **규칙으로 환원되어 코드에 남는가**". 강의도 표준 이론도 후보 — 축당 후보 최대 3 · 근거 필수 · 한 번에 한 축 · 판정은 OOS · 재경쟁은 새 근거가 생겼을 때만("다 성과로 검증하자" 가 무한 실험의 입구).

### 3.5 규제 · 컴플라이언스 · 설명가능성

**자세 한 줄: 규제를 해석하지 않고 회피 구조로 옮겨 놨고, 해석이 필요한 지점은 "법률 검토 필요" 로 명시해 미뤘다.**

- **범위 판단이 문서에 있다.** 스펙 §8: "타인에게 매매 신호 제공·타인 자산 운용 형태의 실제 서비스는 자본시장법상 투자자문업/투자일임업 등록 대상이 될 수 있음. 서비스화 전 범위(**정보 제공 vs 자문 vs 일임**)를 법률 검토 필요. 초기는 '사용자 본인 키로 본인 계좌만'." 국내 규제상 원화 거래소는 마진·선물 불가(현물 전용 어댑터). 서비스 Phase 의 첫 결정(D4-1)이 "서비스 범위를 법적으로 확정한다 — 이 결과가 다른 태스크의 범위를 정한다" 이고 **미착수**다.
- **면책은 한 문장 · 한 출처 · 버전.** "이 화면의 숫자·순위·후보는 정보 제공이며 **투자 권유가 아닙니다**. 투자 판단과 그 결과의 책임은 본인에게 있습니다." — 서버(`common/security/consent.py`)와 화면이 같은 문장인지 시험이 대조하고, 옛 버전 동의는 400. 자동 실행 모드는 별도 동의문.
- **"AI 가 방향·확률을 말하지 않는다" 를 기계화했다.** import-linter 계약 · 확률 대신 과거 빈도 문구 고정 · 달력 자료형에 방향 칸 없음(시험) · 대시보드 숫자는 도구 결과 참조만 · MCP 지시문 "주문을 내는 도구는 없고 사는 것은 사람이 정한다". 승인 게이트를 따로 만들지 않은 이유: "**사람이 사는 것 자체가 승인**이다".
- **설명가능성 = 근거를 지우지 않는 것.** `Evidence(source · family · grade · suppressed_by)` — 접힌 근거를 지우지 않고 표시만("무엇과 무엇이 겹쳤나가 남아야 원인을 되짚는다"). ID 체인 `trace_id → proposal_id → order_id → position_id` 는 손실 귀속 추적의 진입점. `event_logs.actor` 는 계정 표에 외래키를 걸지 않는다("계정을 지운다고 기록에서 사람이 사라지면 안 된다"). 사람의 손그림은 정답이 아니라 **버그 리포트**로 받고 채점 분모로 쓰는 집계 함수를 만들지 않았다.
- **감사 추적은 코드의 선의에 의존하지 않는다.** `event_logs` · `risk_plan_revisions` 는 DB 롤에서 `REVOKE UPDATE, DELETE, TRUNCATE` — "'수정 API 를 안 만들면 되지 않나' 는 누군가 만드는 순간 무너진다". 손절 하향 금지의 **증거**가 `risk_plan_revisions`. 로그 실패가 리스크 감소 행동(손절·청산·스탑 상향·취소)을 막지 않고 **신규 진입만** 보류, 분류를 안 적으면 기본값은 보류. 시크릿은 `SecretStr` repr 로 안 새고, 손익은 감사 권한 없으면 `null` + `redacted` 표식(낙폭·강제청산은 남긴다 — "위험은 성적이 아니라 안전 정보").
- **접근 통제.** 5단(PENDING · VIEWER · TRADER · ADMIN · GUEST) — "승인과 거래 권한은 별개". 시장 축(코인·국내·미국 × 보기·백테스트·거래)과 매매법 축 grant, "모르는 모양은 전부 없음 — None·오타가 문을 여는 쪽으로 읽히면 안 된다". 게스트는 데모 서버에서만 발급, 실계좌 서버는 `@demo` 를 거른다. 실주문 문은 환경 AND 사용자 토글 AND 키.
- **정직한 공백**: 사용자별 자격증명(본인 키 등록)은 **설계만 있고 코드가 없다**(단일 사용자) · 인증 실패 회로차단기 없음 · 키 회전 절차 없음 · 데드맨 알림 보류(7일 넘게 죽으면 브로커 손절 만료 — 사람이 본다) · 보안 점검 문서는 법률 항목을 다루지 않는다.

**면접에서 "적합성 원칙" 이 나오면**: 지금 구조는 자문이 아니라 **본인 계좌·본인 판단 도구**로 범위를 좁혀 놓은 상태이고, 그 좁힘이 코드로 강제된다(주문 도구 없음 · 사람 확인 클릭 · RiskManager SSoT). 타인에게 신호를 주는 순간 정보 제공/자문/일임 어느 칸인지 법률 검토가 선행돼야 한다는 것을 스펙에 적어 뒀다. 설명가능성은 "왜 이 자리인가" 의 근거 등급과 "누가 무엇을 언제" 의 불변 로그 두 층이다.

## 4. 횡단 교훈 — 문서가 스스로 뽑아 둔 것

1. **fail-closed 는 비용이 아니라 시간 절약이었다** — 평문이면 로그인 거부 · 예상 밖 응답 모양이면 예외 · 스키마 불일치면 기동 거부. 조용히 틀리는 대신 멈췄고 원인이 몇 분 안에 나왔다.
2. **배포는 코드가 아니라 전제의 배포다.**
3. **"같은 코드가 테스트넷도 실계좌도"** 는 검증된 경로라는 장점과 **박제된 전제**라는 위험을 함께 준다 — 환경 전환에는 체크리스트가 짝.
4. **재시작 뒤 무엇이 죽는지 표를 먼저 쓴다** — 거래소가 기억하는 것은 안전했고, 어디도 기억 안 하는 것이 사고였다.
5. **안전장치의 거짓 양성은 곧 거래 중단이다** — "정상 운용에서 이 조건이 참이 되는 순간이 있나" 를 먼저 묻는다.
6. **관측은 사용자와 가장 가까운 홉에서** — 서버 프로브 200 은 "서버가 살아 있다" 만 말한다. 브라우저가 끊은 요청은 nginx 에만 499 로 남는다.
7. **1 GB · 버스트형에서는 배포와 폴링이 예산이다** — 판 자체는 코어의 0.3%, 비용은 전부 우리가 만든 부하였다.
8. **사람이 지켜야 하는 절차는 새벽 3시에 깨진다** → 스크립트 안으로.
9. **측정 도구도 검증 대상이다** — KiB 단위 버그가 서버 사양 결정을 흔들 뻔했다.
10. **라이브 결함은 부품별로는 전부 정상이고 조립해서 돌린 뒤에야 보인다** — 그래서 고쳐도 사고 문서를 지우지 않는다("덫의 지도"). 사고 문서는 실측 증거 · 3줄 요약 · 다시 안 나게 하는 자(시험·로그)가 필수.
11. **탐지 주기 = 복구 주기.** 경보가 맞아도 고칠 자리가 없으면 경보는 소용없다.
12. **합이 맞는 것은 상쇄지 동등성이 아니다.** 두 엔진의 총액이 비슷해도 건별로 짝지어 보기 전엔 같은 매매가 아니다.
