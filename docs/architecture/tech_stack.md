# 기술 스택 — 무엇을 왜 골랐나

이 문서는 이 프로젝트가 쓰는 기술을 하나씩 놓고 **무엇인가 · 장점 · 단점 · 왜 골랐나**를 적는다.
장점만 적힌 목록은 광고지 스펙이지 설계 기록이 아니다. 단점을 같이 적어야 나중에 바꿀 때
"무엇을 감수하고 있었는지"를 알 수 있다.

읽는 법 두 가지.

- **기록된 결정**에는 번호가 붙어 있다(D-1 ~ D-15 · [Phase00 결정 기록](../planning/history/Phase00_Foundation_plan.md)).
  그 근거는 당시에 쓴 것을 그대로 옮겼다.
- 번호가 없는 것은 형식 결정 없이 관례로 굳은 것이다. 그런 항목의 "왜"는 **지금 이 프로젝트에서
  실제로 그 역할을 하는 이유**이지, 과거에 회의를 거쳤다는 뜻이 아니다.

이 프로젝트의 제약을 먼저 적어 둔다. 아래 선택은 대부분 이 넷에서 나온다.

| 제약 | 뜻 |
|---|---|
| 진짜 돈이 돌고 있다 | 조용한 실패가 손실이 된다. 안전장치는 기계가 강제해야 한다 |
| 서버가 1 GB 한 대다 | 무거운 것을 못 올린다. 빌드도 서버에서 못 한다 |
| 사람이 하나다 | 운영 부담이 큰 선택은 그 자체로 위험이다 |
| 저장소가 공개다 | 시크릿·주소·매매법이 새면 안 된다 |

## 1. 언어와 런타임

### Python 3.12 (D-7)

**무엇인가.** 백엔드 전부를 쓴 언어다. 버전을 3.12 로 **고정**했다(`.python-version`).

**장점.** 수치 계산(numpy·pandas)과 데이터 도구가 가장 두텁다. 타입 힌트가 성숙해 pyright strict
로 정적 검사를 걸 수 있다. 비동기(asyncio)가 표준에 들어 있어 I/O 를 한 프로세스에서 굴린다.

**단점.** 실행 속도가 느리다. GIL 때문에 CPU 작업이 여러 코어로 안 퍼진다. 우리는 백테스트 같은
CPU 작업에서 이 벽을 실제로 만난다.

**왜 골랐나.** 매매 판단은 지표·통계 계산이고 그 생태계가 파이썬에 있다. 속도 문제는 두 가지로
피했다. ① I/O 는 전부 비동기라 대기 시간이 겹친다 ② 루프 위에서 도는 CPU 작업(세션 걸음)에는
눈금(`step_ms`)을 달아 얼마나 무거운지 본다.

3.13 을 택하지 않은 이유는 기록돼 있다. 바이너리 휠 의존이 많은 프로젝트라 최신 마이너 버전은
휠 배포가 늦는 패키지가 생기고, 그 디버깅은 프로젝트 본질과 무관한 시간 낭비다. 올리는 것은
언제든 가능하다.

### TypeScript (strict)

**무엇인가.** 화면 코드의 언어. 자바스크립트에 타입을 얹은 것이다.

**장점.** 서버가 주는 JSON 의 모양을 타입으로 적어 두면, 서버 응답이 바뀌었을 때 화면이 **빌드
단계에서** 깨진다. 런타임에 빈 화면이 뜨는 대신이다.

**단점.** 타입을 적는 비용이 든다. 서버 타입과 화면 타입이 자동으로 이어지지 않아 손으로 맞춘다
(스키마 생성기를 두지 않았다).

**왜 골랐나.** 이 화면은 돈을 보여 준다. 숫자가 `undefined` 인 채로 그려지면 사람이 잘못된 잔고를
본다. `noUncheckedIndexedAccess` 까지 켜서 배열 접근도 검사하게 했다.

### uv

**무엇인가.** 파이썬 패키지 관리자이자 가상환경 도구다. pip 와 venv 를 대신한다.

**장점.** 압도적으로 빠르고, `uv.lock` 이 의존성을 정확히 고정한다. CI 와 로컬과 서버가 **같은
잠금 파일**로 같은 것을 설치한다.

**단점.** 비교적 새 도구라 자료가 적고, 드물게 도구 체인 가정이 다른 패키지에서 막힌다.

**왜 골랐나.** 재현성이다. 배포가 잦고 서버가 약해서, "내 컴퓨터에서는 됐는데"를 없애는 값이 크다.
`uv sync --locked` 는 잠금 파일과 다르면 실패하므로 조용한 버전 밀림이 없다.

## 2. 백엔드

### FastAPI

**무엇인가.** 파이썬 웹 프레임워크. HTTP 요청을 파이썬 함수로 받는다.

**장점.** 비동기가 기본이라 바깥 API 를 기다리는 동안 다른 요청을 처리한다. 타입 힌트로 요청·응답을
검증하고 문서를 자동 생성한다. 가볍다.

**단점.** Django 같은 통합 프레임워크가 주는 것(관리자 화면, 인증, ORM 연결)이 없어 직접 만든다.
우리 인증·권한·감사 로그는 전부 자체 구현이다.

**왜 골랐나.** 이 서버가 하는 일의 대부분은 **바깥을 기다리는 것**이다. 거래소, 토스, EDGAR, LLM.
동기 프레임워크였다면 판 여섯 개가 서로를 막았을 것이다. 그리고 1 GB 서버에 올릴 만큼 가볍다.

### SQLAlchemy 2.0 (async) + Alembic

**무엇인가.** SQLAlchemy 는 파이썬에서 SQL 데이터베이스를 다루는 라이브러리다. 표 하나를 파이썬
클래스 하나로 선언한다. Alembic 은 그 선언이 바뀌면 DB 구조를 옮기는 스크립트를 만드는 짝 도구다.

**장점.** 컬럼에 타입이 붙어 pyright 가 검사한다(가격이 `Decimal` 인 것을 기계가 안다). 값이 항상
바인드 파라미터로 나가 SQL 인젝션 경로가 없다. 구조 변경이 파일로 남아 서버에 순서대로 적용된다.

**단점.** 배울 것이 많고, 무심코 쓰면 쿼리가 예상보다 많이 나간다(N+1). PostgreSQL 고유 기능은
ORM 이 다 표현하지 못해 일부는 손으로 쓴 SQL 로 내려간다.

**왜 골랐나.** 돈을 다루는 표라서 타입과 마이그레이션 이력이 필요했다. 실제로 봉 표의 월 파티션
DDL 은 ORM 이 만들지 못해 수기 마이그레이션이 맡는데, 그런 예외를 허용하면서도 나머지 표를
타입으로 묶어 주는 것이 이 조합이다. 지금 마이그레이션 129개가 이 저장소의 구조 변경 이력이다.

### psycopg3 (D-2)

**무엇인가.** PostgreSQL 드라이버. SQLAlchemy 밑에서 실제로 DB 와 말한다.

**장점.** 드라이버 하나로 런타임(비동기)과 Alembic(동기)을 모두 처리한다. raw SQL 파라미터 문법이
psql 과 같다.

**단점.** asyncpg 보다 느리다.

**왜 골랐나. 근거는 성능이 아니라 Alembic 이다.** 마이그레이션은 기본이 동기 실행인데 asyncpg 는
동기 모드가 없다. asyncpg 를 택하면 드라이버를 하나 더 깔거나 마이그레이션 설정을 비동기로
개조해야 한다. 그리고 속도는 이 프로젝트의 병목이 아니다 — 적재 속도는 거래소 요율이 정한다.
되돌리기도 쉽다. SQLAlchemy 를 경유하므로 바뀌는 것은 DB 주소와 raw SQL 몇 군데뿐이다.

### redis-py (asyncio) (D-3)

**무엇인가.** Redis 공식 파이썬 클라이언트.

**장점.** 비동기를 기본 제공하고, 필요한 용도 셋(캐시·단일 실행 락·큐)을 모두 덮는다.

**단점.** 제공되는 `Lock` 객체가 우리에게는 안 맞았다.

**왜 골랐나.** 라이브러리의 `Lock` 대신 **직접 `SET NX PX` 와 TTL 갱신 루프**를 썼다. 락을 잃는
순간을 감지해 거래를 즉시 멈춰야 하는데, 라이브러리 Lock 은 그 지점을 노출하지 않는다. 클라이언트는
표준을 쓰되 락의 핵심 논리는 우리가 쥔 것이다.

### httpx + 자체 아웃바운드 층

**무엇인가.** httpx 는 비동기 HTTP 클라이언트다. 우리는 그것을 `common/http` 한 층으로 감쌌다.

**장점(층).** 재시도, `Retry-After` 존중, 요청 예산, 요율 스로틀, 로그가 **한 곳**에 있다. 출처가
늘어도 그 규칙을 다시 짜지 않는다.

**단점(층).** 한 겹이 더 생겨 특수한 요청은 층을 거치게 만드는 손이 든다.

**왜 골랐나.** 층을 만들기 전에는 열한 곳이 각자 재시도를 짰고, 규칙이 제각각이었다. 지금은 주문
클라이언트만 "재시도 안 함"으로 선언한다. 주문이 생겼을지 모르는 5xx 를 층이 삼키면 안 되기
때문이다. 층 밖에서 원시 클라이언트를 만들면 시험이 깨진다.

### structlog

**무엇인가.** 구조화 로깅 라이브러리. 로그를 문장이 아니라 JSON 으로 남긴다.

**장점.** 필드가 고정돼 있어 기계가 센다. 추적 id 체인으로 제안부터 주문, 포지션까지 잇는다.

**단점.** 사람이 raw 로그를 읽기는 덜 편하다.

**왜 골랐나.** 사고가 나면 "그때 무슨 일이 있었나"를 **세어야** 한다. 며칠 전 사고에서 지정가가
언제 채워졌는지를 로그 필드로 분 단위까지 확인했다. 문장 로그였으면 못 했다.

### APScheduler (인프로세스)

**무엇인가.** 주기 작업 스케줄러. 봉 수집, 대조, 리포트를 시간표대로 돌린다.

**장점.** 별도 프로세스나 브로커가 필요 없다. API 프로세스 안에서 돈다.

**단점.** 프로세스가 죽으면 같이 죽고, 여러 인스턴스가 뜨면 중복 실행된다.

**왜 골랐나.** 1 GB 서버에 Celery 와 브로커를 얹을 여유가 없었다. 중복 실행은 Redis 리더 락과
작업별 `max_instances=1` 로 막는다. 죽는 문제는 컨테이너 자동 재시작과 60초 감시자가 받는다.

### MCP SDK

**무엇인가.** Model Context Protocol. 바깥 AI 도구가 우리 서버의 기능을 부를 수 있게 하는 규약이다.

**장점.** Claude Desktop, Cursor, ChatGPT 가 **같은 도구**를 쓴다. 우리 화면 채팅이 쓰는 함수를
그대로 연다. 기존 FastAPI 경로 하나(`POST /mcp`)에 얹혔다.

**단점.** 규약이 젊어 클라이언트마다 지원 범위가 다르다.

**왜 골랐나.** 도구를 두 벌 만들지 않기 위해서다. 인증은 개인 토큰이고 그 토큰으로는 **읽기만**
된다 — 주문 경로는 열지 않는다.

## 3. 프론트엔드

### React 18 + Vite

**무엇인가.** React 는 화면을 부품으로 짜는 라이브러리, Vite 는 그것을 묶어 주는 빌드 도구다.

**장점.** 부품 재사용이 쉽고 자료가 많다. Vite 는 개발 중 새로고침이 즉시다.

**단점.** 상태 관리를 직접 정해야 하고, 무심코 짜면 불필요한 다시 그리기가 생긴다.

**왜 골랐나.** 화면이 같은 부품을 반복해서 쓴다. 차트, 계좌 카드, 펀드 표가 코인과 주식 양쪽에
그대로 재사용된다. 라이브용 화면을 따로 만들었다가 한쪽만 고쳐지는 사고를 세 번 겪은 뒤로,
"같은 화면을 재사용한다"가 이 프로젝트의 규칙이 됐다.

### TradingView Lightweight Charts 5

**무엇인가.** 금융 차트 전용 오픈소스 라이브러리.

**장점.** 봉 차트, 가격선, 마커, 축 라벨이 처음부터 금융용으로 설계돼 있다. 가볍고 빠르다.
캔들 수만 개를 그려도 버틴다.

**단점.** 범용 차트 라이브러리가 아니라 분포도나 산점도는 못 그린다. 커스터마이즈 범위가 좁다.

**왜 골랐나.** 우리가 그려야 하는 것이 정확히 이 라이브러리가 하는 일이다. 콘솔, 판 상세, 차트
분석 주문, 펀드 상세, 백테스트 리포트가 전부 같은 부품을 쓴다. 못 그리는 분포도와 산점도만
apexcharts 로 따로 그린다. 하나로 다 하려다 둘 다 어정쩡해지는 것보다 낫다고 봤다.

원칙 하나가 여기 붙어 있다. **화면은 계산하지 않는다.** 지표와 구조물과 진입·손절선은 서버가
계산한 값을 그대로 옮겨 그린다. 화면이 따로 계산하면 화면과 매매가 갈린다.

## 4. 저장

### PostgreSQL 16

**무엇인가.** 관계형 데이터베이스. 원장, 봉, 재무 사실, 실험 기록, 감사 로그가 여기 있다.

**장점.** 트랜잭션이 견고하고, 파티션·JSONB·권한 같은 기능이 한 제품 안에 다 있다. 자료가 많다.

**단점.** 시계열 전용 DB 보다 봉 조회가 느릴 수 있다. 운영을 우리가 진다(백업·복구·튜닝).

**왜 골랐나.** 한 제품으로 네 종류 데이터를 다 담을 수 있어서다. 봉은 월 파티션으로 쪼개고,
감사 로그는 **DB 권한으로 INSERT 만** 가능하게 막았다. 앱이 실수로 지우려 해도 DB 가 거절한다.
이런 것을 앱 코드가 아니라 DB 가 강제하는 것이 이 선택의 값이다.

시계열 DB(TimescaleDB) 전환은 "봉 조회가 느려지면" 이라는 방아쇠와 함께 적어 두고 미뤘다.
아직 그 시점이 오지 않았다.

### Redis

**무엇인가.** 메모리에 사는 열쇠-값 저장소. 값마다 수명을 걸 수 있다.

**장점.** 매우 빠르고, "없으면 만들고 있으면 실패"를 한 번의 원자적 동작으로 한다. 수명이 지난
값은 알아서 사라진다.

**단점.** 메모리라서 재시작하면 비고, 이론적으로 락이 겹치는 창이 있다.

**왜 골랐나.** 세 가지를 맡긴다. ① 거래 리더 락 — API 두 슬롯 중 하나만 매매하게 한다 ② 자원
비트 — 엔진이 30초마다 상태를 써 두면 화면이 그것만 읽는다 ③ 스크리닝 결과 사본 — 배포로
프로세스가 새로 떠도 화면이 비지 않는다.

**잃어도 되는 것만 둔다**는 것이 이 선택의 전제다. Redis 가 죽어도 거래는 멈추지 않는다. 손절
관리를 한 번 끊겼다고 중단하는 쪽이 더 위험하기 때문이다. 다만 락을 **잃으면** 즉시 멈춘다 —
다른 인스턴스가 이미 리더일 수 있다. 연결이 끊긴 것과 락을 잃은 것을 다르게 다룬다.

그리고 락은 중복 주문의 최종 방어선이 아니다. 그것은 주문 이름에 넣는 멱등키다. 락은 낭비와
혼선을 줄이는 장치다.

## 5. AI

### NVIDIA NIM (모델 풀)

**무엇인가.** 여러 오픈 모델을 API 로 부를 수 있게 호스팅한 서비스다. GPU 를 우리가 사지 않는다.

**장점.** 모델을 설정 파일에서 갈아 끼운다. 한 모델이 실패하면 다음으로 넘어가는 사슬을 뒀다.
1 GB 서버에 모델을 올릴 수 없으니 이것 말고는 방법이 없었다.

**단점.** 모델이 예고 없이 폐기된다(410). 응답 시간 편차가 크다. 바깥 서비스라 우리가 못 고친다.

**왜 골랐나.** 원가와 교체 가능성이다. 실제로 풀의 열 종 중 일곱이 폐기된 적이 있어, 살아 있는
것만 실호출로 확인해 남겼다. 모델을 하나에 묶지 않은 설계가 그때 값을 했다.

### 자체 에이전트 루프 (LangGraph 미채택)

**무엇인가.** 질문 → 계획 → 도구 → 종합의 왕복을 도는 코드. 프레임워크 없이 직접 짰다.

**장점.** 무엇이 언제 불리는지 전부 우리 코드다. 왕복 상한, 도구 결과 압축, 실패 처리, 기록을
원하는 대로 넣었다. 의존성이 하나 줄었다.

**단점.** 프레임워크가 주는 것(그래프 시각화, 체크포인트, 분기)을 직접 만들어야 한다.

**왜 골랐나.** 기록된 판단은 이렇다. **정확도는 프레임워크가 아니라 모델·프롬프트·도구가 주는
사실과 검증에서 나온다.** 우리가 해결해야 했던 문제는 "AI 가 지어낸 숫자를 말하는 것"이었고, 그
답은 그래프 엔진이 아니라 대시보드 값에 도구 결과 참조만 허용하고 근거 없는 칸을 세는 규칙이었다.

## 7. 인프라

### AWS Lightsail (1 GB · 도쿄)

**무엇인가.** 고정 가격 가상 서버. 월 $7 짜리 한 대를 쓴다.

**장점.** 값이 예측된다. 관리 콘솔이 단순하다. 스냅샷 백업이 한 번에 된다. 도쿄라 거래소까지
지연이 짧다.

**단점.** 1 GB 는 정말 작다. 여기서 도커 빌드를 못 한다. 수직 확장 말고는 늘릴 방법이 없다.

**왜 골랐나.** 자본이 300 USDT 인 계좌에 월 수십 달러짜리 인프라를 붙이는 것은 앞뒤가 안 맞는다.
대신 작은 서버를 전제로 설계를 맞췄다. 빌드는 로컬에서 하고 이미지를 전송한다. 폴링 주기와 캐시를
조여 메모리를 지킨다. 빌드 컨텍스트를 14 GB 에서 5 MB 로 줄인 것도 이 제약 때문이다.

### Docker Compose (base + override) (D-10)

**무엇인가.** 컨테이너 여러 개를 한 파일로 정의해 함께 띄우는 도구다.

**장점.** 개발·데모·실계좌가 **같은 서비스 정의**를 쓰고 차이(환경 파일, 소스 마운트, 자원 제한)만
덧씌운다. 한 대짜리 서버에 딱 맞는 무게다.

**단점.** 여러 대로 늘릴 수 없다. 무중단 배포를 직접 만들어야 한다.

**왜 골랐나.** 환경별로 파일을 복제하지 않기 위해서다. 복제하면 포트나 헬스체크를 고칠 때 세 곳을
고쳐야 하고, 한 곳을 빠뜨리면 **개발에서는 되는데 실계좌에서 안 되는** 최악의 버그가 생긴다.

쿠버네티스는 검토 대상이 아니었다. 노드 하나에 사람 하나인데 운영 부담만 늘린다.

### 블루그린 배포 (자체 구현)

**무엇인가.** API 슬롯 두 개를 번갈아 쓰는 배포 방식이다. 새 슬롯을 먼저 띄우고 확인한 뒤 교체한다.

**장점.** 배포해도 거래가 끊기지 않는다. 실패하면 옛 슬롯을 그대로 둔다.

**단점.** 직접 만들어야 했다. 교체 순간 두 이미지가 같은 DB 를 보므로 마이그레이션은 하위 호환만
허용된다. 교체 창 수십 초 동안 짧은 오류가 난다.

**왜 골랐나.** 목표가 "프로세스가 안 죽는다"가 아니라 **"거래 리더가 끊기지 않는다"** 였기 때문이다.
새 슬롯은 팔로워로 뜨고, 옛 슬롯이 락을 놓으면 승격해 열린 판을 입양한다. 2026-09-11 하루에 열 번
배포하는 동안 판 여섯 개가 매번 이어졌다.

### Caddy + nginx

**무엇인가.** Caddy 가 바깥에서 TLS 를 맡고, nginx 가 정적 파일과 API 분기를 맡는다.

**장점.** Caddy 는 인증서를 자동으로 받고 갱신한다. nginx 는 쿠키로 실계좌 API 와 데모 API 를
가르고, 접근 로그가 화면 문제를 푸는 첫 단서가 된다.

**단점.** 프록시가 둘이라 "왜 둘이냐"를 설명해야 한다. 계층이 하나 늘면 오류의 출처도 늘어난다
(502 가 nginx 것인지 앱 것인지 가르는 로그 형식을 따로 만들었다).

**왜 골랐나.** 역할이 다르다. 인증서 자동화는 Caddy 가 압도적으로 편하고, 정적 파일 서빙과 경로
분기는 nginx 가 익숙하고 세밀하다. 하나로 합칠 수는 있지만 둘 다 잘하는 일을 맡기는 쪽을 택했다.

## 8. 품질 게이트

| 도구 | 무엇 | 장점 | 단점 | 왜 |
|---|---|---|---|---|
| ruff | 린트와 포맷 | 매우 빠르고 둘을 한 도구가 한다 | 규칙이 자주 바뀐다 | 검사가 느리면 아무도 안 돌린다 |
| pyright (strict) | 파이썬 타입 검사 | `Any` 유입을 막는다 | 엄격해서 우회 코드가 는다 | 돈을 다루는 값의 타입이 뭉개지면 안 된다 |
| import-linter | 계층 의존 검사 | 설계 규칙을 **기계가** 지킨다 | 계약을 손으로 적어야 한다 | 분석이 집행을 부르는 경로가 생기면 설계가 무너진다 |
| pytest | 시험 | 자료가 많고 확장이 쉽다 | 느려지기 쉽다 | 3,800여 개가 1분 안에 돈다 |
| vitest | 화면 시험 | Vite 와 같은 설정을 쓴다 | 브라우저 실동작은 못 본다 | 계산이 아니라 표시 규칙을 지킨다 |
| pre-commit | 커밋 훅 | 잘못된 것이 저장소에 안 들어간다 | 커밋이 느려진다 | 공개 저장소라 시크릿 한 번이 치명적이다 |
| GitHub Actions (D-1) | CI | push 마다 같은 검사 | 유료이고 지금은 멈춰 있다 | 지금은 로컬 `ci_local.sh` 가 같은 순서를 돈다 |

여기에 **AST 검사 셋**이 더 있다. 라이브러리가 아니라 우리가 쓴 시험이다.

- 실주문 어댑터를 게이트 밖에서 만들면 실패한다.
- 원시 HTTP 클라이언트를 아웃바운드 층 밖에서 만들면 실패한다.
- 나간 요청으로 주문 서명을 다시 계산해 맞는지 본다.

규칙을 문서로만 적으면 언젠가 깨진다. 기계가 읽을 수 있는 형태로 옮기는 것이 이 프로젝트의 방식이다.

## 9. 쓰지 않기로 한 것

고른 것만큼 안 고른 것도 기록이다.

| 후보 | 왜 안 썼나 |
|---|---|
| LangGraph (에이전트 프레임워크) | 정확도는 프레임워크가 아니라 모델·프롬프트·도구가 주는 사실과 검증에서 나온다고 판단했다. **멀티 에이전트로 가면서 다시 물었고 답은 같았다** — 우리 위상이 부채꼴(분기·순환 없음)이고, 프레임워크가 끌고 오는 모델 클라이언트가 아웃바운드 층을 지나지 않는다. 근거와 **다시 꺼낼 조건 셋**은 [ai_agents_and_mcp §3.1](ai_agents_and_mcp.md) |
| asyncpg | 더 빠르지만 동기 모드가 없어 마이그레이션 설정이 복잡해진다. 속도는 우리 병목이 아니다 |
| 쿠버네티스 | 서버 한 대, 사람 한 명. 운영 부담만 는다 |
| Celery 등 작업 큐 + 브로커 | 1 GB 에 프로세스를 더 못 올린다. 인프로세스 스케줄러 + 리더 락으로 충분했다 |
| 관리형 DB(RDS 등) | 월 비용이 서버 값을 넘는다. 자본 300 USDT 계좌에 맞지 않는다 |
| TimescaleDB | 아직 봉 조회가 병목이 아니다. 방아쇠를 적어 두고 미뤘다 |
| 지표 라이브러리(pandas-ta 등) | 지표는 자체 구현한다. 라이브러리 정의가 바뀌면 과거 측정이 재현되지 않는다(대조용으로만 쓴다) |
| 브라우저 팝업(confirm·alert) | 되돌리기 어려운 조치는 화면 안 확인 패널로 받는다 |
