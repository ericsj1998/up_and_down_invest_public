# 원장과 거래소를 어떻게 맞추나 — 대조 · 장애 · 영속성

> 이 문서는 **애플리케이션의 실제 프로세스**를 설명한다. 주문 하나가 나갈 때 무엇을 확인하고, 거래소와 원장이 갈리면 어떻게 알고, 서버가 죽었다 살아나면 무엇이 어디에서 복원되는가. 규칙의 근거는 전부 실제 사고다(§8).

---

## 0. 용어

| 용어 | 뜻 | 어디에 |
|---|---|---|
| **원장(Ledger)** | 앱이 믿는 매매 기록. `TradeRecord` 하나가 계획(진입·손절·1차·목표)과 실제(체결가·청산가·결과)를 나란히 든다 | 메모리(`Session.ledger`) + `wf_trades` |
| **판(RUN)** | 종목 하나에 매매법 하나를 굴리는 단위. 러너(`LiveRunner`) 하나가 붙는다 | `wf_runs` + api 프로세스 메모리 |
| **닻(anchor)** | `market:symbol:playbook:live`. **열린 판은 닻당 하나**. 재시작해도 같은 닻의 열린 행을 이어받는다 | `wf_runs.anchor` |
| **거래소 사실** | 포지션 스냅샷 · 열린 주문(조건부·지정가) · 체결/청산 이력 | 거래소 API |
| **판 표식 · 매매 id** | 주문 이름(`text`)에 박히는 `t-<판6자>-<매매8자>-<종류>-<다리>`. 멱등키이자 **소유권 증명** | 거래소 주문 · `wf_orders` |
| **대조(reconcile)** | 원장과 거래소 사실을 맞춰 보는 일. **자동 수정이 아니다** | `orchestration/reconcile.py` · `LiveRunner.reconcile` |
| **입양(adopt)** | 거래소에 이미 있는 포지션·주문에서 계획을 **되읽어** 원장에 넣는 일 | `LiveRunner.adopt` |

## 1. 문제의 뿌리 — 진실이 둘이다

원장은 **의도**, 거래소는 **사실**이다. 둘은 다음 이유로 갈린다.

1. **시점** — 우리 청산 판정은 진입축 봉 마감(4h·15m)에 돌고, 브로커 조건부 손절은 가격이 닿는 **순간** 나간다. 그 사이 원장은 "보유", 거래소는 "없음".
2. **기억의 위치** — 판 세션은 api 프로세스 메모리에 산다. 리로드·배포·재부팅이면 사라진다. 포지션은 거래소에 남는다.
3. **부분 체결** — 손절 118 계약 중 35 만 체결되고 83 은 거래소 가격보호에 죽었다(08-26). 원장은 "손절됨", 거래소는 "83 계약 무방비".
4. **만료** — Gate 조건부는 조용히 만료된다(기본 24시간 · 우리는 30일 · 7일 전 갱신). 만료는 아무 신호도 내지 않는다.
5. **사람** — 거래소 웹에서 직접 닫거나, 다른 프로세스(같은 계정의 다른 스택)가 손댄다.
6. **강제청산** — 우리 주문이 아닌 `ao-` 청산이 생긴다. 원장은 모른다.

어느 쪽을 진실로 볼지는 상황마다 다르다. 그래서 **자동 싱크를 만들지 않았다.**

```
원장을 자동으로 고친다   → 같은 입력에 다른 원장 = 결정론이 깨진다 (규칙 #5)
거래소를 자동으로 닫는다 → 손익이 사람 모르게 확정된다. 되돌릴 수 없다
```

⇒ **거래소는 사실, 원장은 의도.** 사실이 바뀌면 원장을 사실로 **끌어당기되 값을 지어내지 않는다**(청산가는 체결 이력에서만). 갈렸는데 사실을 못 읽으면 **멈추고 사람에게** 넘긴다.

## 2. 주문 하나가 나갈 때 — 실제 절차

`_live_start`(판 시작)와 `LiveRunner._walk_once`(걸음)가 하는 검사를 순서대로 적는다. 시퀀스 그림은 [diagrams.md §3.1](diagrams.md#31-한-판의-한-걸음--판정--주문--보호--대조).

### 2.1 판을 띄우기 전 (한 번)

| 순서 | 검사 | 통과 못 하면 | 왜 |
|---|---|---|---|
| 1 | **이 API 가 연결한 거래소인가** (`UPDOWN_MARKETS` 안 · 키로 어댑터를 얻을 수 있나) | 400 | 같은 계정을 다른 프로세스가 관리할 수 있다 — 관리자 둘은 손절·진입·회수가 겹친다 (09-06 실사고) |
| 2 | **같은 거래소·종목의 열린 판**이 있나 (`holder_of`) | 409 | Gate 무기한은 종목당 포지션이 하나 — 두 판이 서로의 포지션을 자기 것으로 여긴다 |
| 3 | **유동성** — 그 판의 명목(증거금×배율)을 호가창이 받나 (`probe_book` · 주문 거래소의 호가) | 409 | 조회용 라이브 호가는 testnet 과 다르다. SPCX 증거금 420 이 15시간 묶였던 사고 |
| 4 | **1계약 예산** — 다리 하나 예산으로 최소 계약을 살 수 있나 (`sizing_of`) | 409 | 자리가 좋아도 못 산다. 7시간 0건 뒤에야 알던 것을 띄우는 순간에 막는다 |
| 5 | **잔재 회수** — 그 종목에 포지션 없이 남은 조건부·지정가 (`sweep_leftovers`) | 회수 | `size:0` 조건부는 새 포지션을 통째로 닫는다. **포지션이 있으면 아무것도 거두지 않는다** |
| 6 | `RunStore.open` — 같은 닻의 열린 판이 있으면 **이어받고** 없으면 연다 | — | 옛 키·시드·증거금이 새 값을 이긴다. 다른 조건이면 닫고 새로 연다 |

### 2.2 걸음마다 (진입축 봉 마감)

1. `Session.step()` — 동기·순수. 제안 → 계획(진입가·`planned_stop`·`planned_first`·`planned_target`). 여기서 거래소를 부르지 않는다.
2. 러너가 계획을 **주문으로 사상**(`order_mapping`) — 원장에는 수량이 없다(퍼센트 원장). 계약은 정수라 반올림 드리프트가 생기고, 그 차이를 **기록**한다(감추면 "라이브가 백테스트보다 나쁘다" 의 원인을 전략으로 오해한다).
3. **증거금**으로 수량을 계산한다(지갑 전액이 아니다) · 거래소 요구 증거금은 우리 계산보다 크다(표시가·수수료) → 라이브만 여유를 둔다.
4. 주문 전송 — `text = t-<판6>-<매매8>-<종류>-<다리>` (멱등키). 브로커가 같은 키의 두 번째를 거부한다. **중복 주문의 최종 방어선은 락이 아니라 이 키다.**
5. 요청·응답 원문을 `wf_orders` 에, 의도가·체결가·수량을 `wf_calibration` 에 적는다.
6. 대기 계획(`_waiting`·`_tickets`·`_waiting_until`)을 `wf_runs.meta_json["pending_entry"]` 에 **걸음마다** 저장한다(T218).

### 2.3 체결 뒤 — 보호

1. 체결은 러너가 폴링해 **우편함**(`LiveFiller.note`)에 넣고, 세션이 다음 걸음에 `poll()` 로 꺼내 원장에 적는다. 세션은 "샀나" 를 **판정하지 않는다** — 거래소가 이미 답했다.
2. **조건부 손절**(`trigger = planned_stop` · `size 0` 전량) + **익절 reduce-only 지정가** 를 건다. 손절 가격은 원장이 정한다(규칙 #4). 러너는 옮기기만.
3. `_guard_stop` — 포지션이 있으면 **거래소에 조건부가 걸려 있는지 묻고** 없으면 건다. "걸었다" 를 기억하지 않는다(만료를 우리 기억은 모른다). 걸음마다 + **30초 점검**마다.
   - 30초 루프에서는 연속 실패 카운터를 올리지 않는다. 그 문턱은 걸음 단위로 고른 값이라 30초에 그대로 두면 레이트리밋 세 번에 90초 만에 시장가로 던진다.
4. 원장을 DB 에 **통째로** 다시 쓴다. 실패해도 던지지 않는다 — 저장 실패가 손절·청산을 막으면 안 된다(§1.2.1 · 규칙 #8-1). 로그로 크게 남기고 다음 걸음에 다시 쓴다.

### 2.4 거래소가 먼저 닫았을 때 — 30초 대조

`LiveRunner.reconcile` (30초 · `_keep_probing`):

```
원장에 OPEN 매매가 있다 → 포지션 스냅샷 size == 0 ?
  → 체결 이력에서 그 매매의 청산 체결가를 찾는다
      못 찾으면 → 닫지 않고 감사(ledger_mismatch)에 넘긴다  ⛔ 값을 지어내지 않는다
      찾으면   → 방향·가격으로 TP/SL 판정 · 강제청산 이력이 있으면 LIQUIDATED
  → 원장 마감 · 세션 release · 로그 live_reconciled
```

이것은 **판정이 아니다.** 진입 판단은 여전히 봉 마감에서만 돈다. 둘을 섞으면 라이브와 백테스트가 다른 규칙이 된다.

### 2.5 전 거래소 대조 — 120초

`reconcile_once` 가 거래소마다 포지션·열린 주문·청산 이력을 **한 번의 조회**로 받아 `(거래소, 종목)` 칸을 만들고 순수 함수 `compare()` 에 넣는다. 반쪽 대조는 성공으로 세지 않는다(못 본 거래소의 고아를 "없다" 로 읽는 것이 최악).

| 축 | 거래소 | 원장 | 등급 | 자동 처리 | 사람 |
|---|---|---|---|---|---|
| **A 무주공산** | 포지션 있음 | 없음 | error | 없음 | 콘솔에서 **이어받기**(adopt) 또는 **닫기** |
| **B 유령 원장** | 없음 | 보유 중 | error | 30초 대조가 실제 체결가로 마감 | 체결가를 못 찾으면 사람 |
| **C 잔재** | 주문만 · 맡은 판 없음 | 없음 | warn | 판 시작 시 자동 회수 | 콘솔 "거두기" (포지션이 없어 안전) |
| **D 부분 무방비** | 보유 N · 조건부가 덮는 건 M<N | 보유 | error | 30초 점검이 손절 재장착 시도 | 확인 |

- 갈린 종목의 세션에 `reconciled=false` 를 꽂아 **그 종목의 신규 진입을 막는다**. 세션은 API 를 모르므로 값만 받는다(계층 유지).
- 보호 물량을 **못 셌으면** `UNKNOWN(-1)` 이다. 0(보호 없음)과 섞으면 조회 실패가 곧 "무방비" 가 되어 멀쩡한 판을 막는다.
- 결과는 파일에도 저장한다(`_save_reconcile`) — 재시작 직후 "아직 안 봤다" 와 "봤는데 괜찮다" 를 가른다.

### 2.6 손익 귀속 — 내 것만 센다

한 계정에 여러 판 · 강제청산 · 수동 정리가 며칠치 쌓인다. `attribute_closes` 규칙:

- 주문 이름에 **내 판 표식**이 있으면 → 내 것.
- 태그가 없으면(`ao-` 강제청산 · 수동청산) → **내가 그 계약을 들고 있던 시간창** 안이면 내 것. 창 밖은 이전 소유자의 잔재.
- 재정렬(resync) 워터마크 이전은 전부 무시(복구 불가한 과거).

내가 강제청산됐는데 원장이 놓쳤으면 이제 정확히 "너 청산됐는데 원장은 모른다" 로 잡힌다(예전엔 태그 없다고 빼서 놓쳤다).

## 3. 서버가 죽었을 때

### 3.1 무엇이 돈을 지키나 — 층별

| 층 | 살아 있을 때 | 죽었을 때 | 한계 |
|---|---|---|---|
| 우리 손절 감시(러너) | 30초 점검 · 트레일 상향 · 반익 | **멈춘다** | — |
| **브로커 조건부 손절** | 걸음·30초마다 존재 확인 · 재장착 | **거래소가 집행한다** — 유일한 방어선 | 30일 만료(7일 전 갱신). 7일 넘게 죽으면 만료 |
| 컨테이너 | `restart: always` · 헬스체크 | Docker 가 재시작 | 인스턴스 정지·네트워크 단절은 못 본다 |
| 거래 리더 락 | 하트비트 갱신 | 팔로워가 5초 안 승격 | 두 슬롯이 다 죽으면 브로커 손절만 남는다 |
| DB | 원장·판 메타·대기 계획 | 러너는 브로커 손절이 지키고 `fund_retry_loop` 재시도 | 복구 지연 |
| 데드맨 알림 | — | **없음**(보류 · 사용자 결정) | 사람이 리포트 메일·화면으로 본다 |

### 3.2 영속 등급 — 무엇이 어디에 기억되나

| 상태 | 기억하는 곳 | 재기동 뒤 | 근거 |
|---|---|---|---|
| 포지션 | 거래소 | `adopt` 가 되읽어 입양 | 08-18 · 09-05 첫날 실측 |
| 조건부 손절 | 거래소 | 계획을 되읽어 다시 건다 · 만료 7일 전 갱신 | 갭 2 |
| 열린 진입 지정가 | 거래소 | 멱등키 접두 + 저장된 계획이 맞으면 **이어받음**, 아니면 좀비로 취소 | T218 · F1 |
| 대기 진입 **계획** | DB `wf_runs.meta_json.pending_entry` | 복원 · 복원 직후 한 걸음은 거래소 상태를 먼저 읽는다 | T218 |
| 판 메타 · 원장 · 매매 · 주문 원문 · 캘리브레이션 | DB `wf_*` | 그대로 | — |
| 펀드(판 묶음 · 예산 배분) | JSON 파일 `logs/funds/*.json` | `restore_funds` · 실패하면 `PENDING_FUNDS` 에 남겨 120초마다 재시도 | 예산 안 붙은 판은 계좌 전액을 자기 것으로 센다 |
| 대조 결과 | 파일 | 읽어서 "아직 안 봤다" 와 가른다 | — |
| 지표 · 폴링 캐시 · 레이트리밋 계측 | 메모리 | 잃어도 됨 | — |

### 3.3 부팅 순서 — 등급이 정한다

```
migrate(alembic upgrade head · 하위 호환)  →  api 기동
  → TradingLeader.begin()  (Redis SET NX · 리더/팔로워)
  → [리더] autostart_live: open_runs(closed_at IS NULL) 를 판마다 _live_start(reviving=True)
        · adopt: 포지션 + 조건부에서 계획 되읽기 (손절 없으면 입양 거부)
        · restore_pending: meta_json 의 대기 계획 vs 거래소 열린 주문 — 표마다 이어받기/재요청/체결로/버리기
        · 좀비 정리: 내 접두인데 대조에 없는 지정가 취소
  → restore_funds (펀드 JSON → 판 핸들)
  → watch_forever(60s): DB 의 열린 판 기준으로 러너 없음·태스크 죽음·걸음 정지·봉 정지를 가른다 · 되살리기(백오프)
  → reconcile_loop(120s) · daily_report_loop
```

- 되살리기 조건은 "테스트넷 자격증명이 하나라도" 다 — 09-06 까지 Gate 키 하나에 묶여 있어 키가 없으면 다른 거래소 판까지 관리 밖에 놓였다(수정됨).
- 감시자는 **메모리가 아니라 DB** 를 기준으로 본다. 메모리 기준이면 사라진 판은 목록에도 없어 영원히 안 보인다(08-19 실측).
- 배포는 블루그린 — 새 슬롯 healthy·팔로워 확인 → 옛 슬롯 stop(grace 30s · 락 해제) → 승격 → 입양. 2·4 단계 실패 시 새 슬롯을 내리고 옛 슬롯 유지. 마이그레이션은 두 이미지가 같은 DB 를 쓰므로 **확장 → 배포 → 수축**.

### 3.4 Redis · DB 불통 정책

- **Redis 불통**: 거래를 막지 않는다. 손절 관리를 Redis 한 번 끊겼다고 멈추는 것이 더 위험. 크게 경고하고 그 창의 이중매매 위험은 감수한다(락은 낭비·혼선을 줄이는 장치, 돈의 안전은 멱등키).
- **DB 불통**: 원장 저장 실패는 로그로 남기고 매매는 계속. 리스크 감소 행동은 저장 없이도 나간다. 신규 진입만 보류.
- 락 **상실**은 즉시 정지다 — 갱신 실패를 감지하면 거래 루프를 멈춘다. 재시도하며 버티면 다른 인스턴스가 이미 리더로 일하고 있을 수 있다.

## 4. 영속성 설계의 선택들

| 선택 | 이유 |
|---|---|
| 원장을 **통째로 다시 쓴다**(이어쓰기 아님) | 한 판의 매매는 수십 건. 이어쓰기로는 대기 → 체결 → 청산 갱신을 표현할 수 없다 |
| 행을 **지우지 않는다** | 원장에서 사라진 매매가 DB 에 남는 것이, 있지도 않은 매매가 지워지는 것보다 낫다 — 전자는 눈에 띄고 후자는 안 띈다 |
| 닫힌 판도 남긴다(`closed_at` · `closed_reason`) | "어제 뭘 했나" 에 답하는 것이 표의 존재 이유 |
| `event_logs` · `risk_plan_revisions` 는 DB 권한으로 **INSERT 만** | 감사 로그·손절 개정 이력은 사후 수정 불가여야 한다(규칙 #8-2). 코드가 아니라 DB 가 강제 |
| 로그 적재 실패 → 폴백 파일 → 복구 롤(`GRANT SELECT, INSERT`)이 이관 | 로그 때문에 매매가 멈추면 안 되고, 로그를 잃어도 안 된다 |
| 주문 원문(`raw_json`)을 저장 | 거래소가 무슨 말을 했는지 없으면 "왜 거절됐나" 를 영영 모른다 |
| 계획과 실제를 같은 행에 | 결과만 재는 표는 계획 결함(RR 174 · 손절폭 < 비용)에 눈이 없다 |
| 봉은 **거래소 klines 를 직접** 읽는다(`candles` 표 미사용) | 라이브 DB 에는 봉이 0건. 분석·백테스트와 라이브의 봉 출처가 다른 것은 열린 문제(F5) |
| 백업 | pg_dump 일 1회(7일) + Lightsail 디스크 스냅샷(서버 밖) · `restore.sh` 리허설 11초 |

## 7. 남은 한계 (알고 있는 것)

- 앱이 **7일 넘게** 죽으면 브로커 손절이 만료된다. 데드맨 알림은 보류 상태.
- 인증 실패(401/403) 회로차단기 없음 — 밴 회로차단은 있다.
- 계정 UUID 기준 "관리 호스트" 가드 없음 — 같은 계정에 두 스택이 붙는 것을 코드가 막지 못한다.
- 영속 등급 표는 사람이 쓴 표다. 필드마다 등급을 붙이고 시험으로 고정하는 일이 남았다(G6).
- 대조는 4축이지만 **부분 체결 진입**(지정가가 반만 채워진 뒤 재시작)은 `pending_entry` 복원 경로에 의존한다 — 표로 시험은 있으나 실전 표본은 아직 1건.
