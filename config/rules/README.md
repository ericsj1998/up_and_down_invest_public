# `config/rules/` — 셋업 룰 설정 (D1-1)

**파라미터의 1차 소스는 이 디렉터리다. DB 오버라이드 경로는 없다.**

편의성 판단이 아니라 spec §5.6.2 를 구조로 강제하는 선택이다 — 실행 중에 파라미터를
바꿀 수 있으면 그것이 곧 "성과를 보고 몰래 조율하는" 경로다. YAML 은 변경이 **커밋으로
남아** 누가·언제·왜가 보이고, 커밋 해시 하나로 당시 파라미터가 복원된다.

근거 상세: [Phase01_Analysis_Backtest.md §1-0d](../../docs/planning/history/Phase01_Analysis_Backtest.md)

---

## 파일 1개 = 룰 1개

플러그인 추가는 세 조각이다 (spec §4.3.1 "탐지 파일 1개 + 레지스트리 1줄"):

1. `src/updown/analysis/detectors/<rule_id>.py` — 탐지 로직
2. `src/updown/analysis/detectors/registry.py` 의 `BUILTIN_DETECTORS` 에 **한 줄**
3. `config/rules/<rule_id>.yml` — 이 파일

**파일명과 `rule_id` 가 다르면 로더가 거부한다.** 파일을 복사해 새 룰을 만들다 `rule_id`
를 안 바꾸는 실수를 잡는다.

셋 중 하나라도 빠지면 레지스트리가 예외를 던진다 — 설정만 있고 코드가 없거나, 코드만
있고 설정이 없는 상태를 조용히 넘기지 않는다 (절대 규칙 #8).

## 스키마

```yaml
rule_id: order_block          # 필수. 파일명과 같아야 한다
version: "1.0.0"              # 필수. 성과가 rule_id@version 단위로 귀속된다 (§4.14)
enabled: true                 # 생략 시 true
buckets: [scalp, swing]       # 필수. 비우면 어디에도 적용되지 않는다
params:                       # 생략 가능
  lookback_bars: 20
  volume_multiple: 2.0        # float 는 Decimal 로 승격된다
```

| 키 | 성격 |
|----|------|
| `version` | **파라미터를 바꾸면 함께 올린다** (§5.6.2). 그래야 성과 집계가 갈라진다 |
| `enabled` | §4.6 브레이커 ②(룰 자동 비활성)가 끄는 스위치. **굵은 단위 적응이라 허용된다** |
| `buckets` | 기본값을 "전 버킷"으로 두지 않는다 — 단타용 룰이 장투에 조용히 적용되면 안 된다 |
| `params` | **스칼라만.** 중첩 구조가 필요하면 그것은 파라미터가 아니라 룰 설계 문제다 |

## 값은 표준 이론값으로 고정한다 ⚠️

spec §5.6.1 ② — 성과를 보고 미세조정하지 않는다. 바꿀 때는 사람이 백테스트로 검증하고
`version` 을 올려 커밋한다. 각 값에 **왜 그 값인지 주석**을 남긴다.

임계값의 출처가 스펙에 없으면 숫자를 만들지 말고 계획 문서의 `[결정 필요]` 로 올린다.
(예: "크로스 + 거래량 동반"의 배수 — `docs/rules/indicator_rules.md` §5)

## 지금 이 디렉터리에 룰 파일이 없는 이유

셋업 플러그인은 **P1-5~P1-10** 에서 만든다. P1-3 은 계약과 배선을 세우는 단계다.

**예시 YAML 을 미리 넣지 않는다.** 레지스트리는 "설정만 있고 코드가 없는" 상태를 예외로
거부하므로(위 참조), 짝 없는 예시 파일을 두면 부팅이 깨진다. 그 검사를 약화시키는 대신
**스키마는 이 문서에, 동작 증명은 테스트에** 둔다
(`tests/test_registry_and_context.py` — 더미 플러그인 1개 + 등록 1줄로 파이프라인 편입 증명).
